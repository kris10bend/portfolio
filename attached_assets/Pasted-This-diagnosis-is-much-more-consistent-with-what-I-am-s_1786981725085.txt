One important concern with the proposed fix

Before implementing the ByteLimitTransform workaround, please verify its bandwidth implications.

If we request:

Range: bytes=0-65535

and then call GCS createReadStream({ start: 0 }), GCS may stream from byte 0 all the way to the end of a 63 MB video, while the ByteLimitTransform only forwards the first 65,536 bytes to the browser.

That would avoid the GCS start/end stall, but it could cause the server to read a very large amount of unnecessary data from Object Storage for every small browser range request.

Please determine whether the underlying GCS stream can be safely terminated immediately after the ByteLimitTransform reaches its limit, and whether destroying the upstream stream actually stops the Object Storage transfer.

If it does NOT reliably stop the upstream transfer, please quantify the downside and determine whether there is a better production-safe approach.
